# Codeg-Fork user and developer guide

Codeg-Fork is the `codeg-ios-fork` distribution of
[Codeg for iOS](https://github.com/xintaofei/codeg-ios), with modifications by
PanAndDuck under [Apache-2.0](../LICENSE). See [NOTICE](../NOTICE) and
[third-party notices](../THIRD_PARTY_NOTICES.md) for attribution.

## Server compatibility

Stock codeg supports LAN connections and basic features. Relay pairing requires
a codeg server with the built-in relay client implementing the
`/__codeg_relay/v1` protocol. Use pairing data generated by that server; a plain
reverse proxy alone does not provide the relay pairing protocol.

Optional features depend on the server's API support. Servers without transcript
window metadata are treated as returning complete history. A 404 or 501 from a
chat-creation endpoint disables folderless chat for the current server transport
lifetime; ordinary network failures remain retryable.

## Flavor and app isolation

The fork installs alongside the official app (`app.codeg.ios`). It has a separate
app container, UserDefaults domain, and default Keychain access group.

| Build setting | Official default | Fork script |
| --- | --- | --- |
| `CODEG_DISPLAY_NAME` | `Codeg` | `Codeg-Fork` |
| `CODEG_BUNDLE_ID` | `app.codeg.ios` | `app.codeg.ios.fork$(CODEG_BUNDLE_ID_SUFFIX)` |
| `CODEG_URL_SCHEME` | `codeg` | `codegfork` |
| `CODEG_FLAVOR` | `official` | `fork` |
| `CODEG_BUILD_COMMIT` | empty | current short Git SHA |

`project.yml` keeps the official defaults. `scripts/build-fork.sh` supplies fork
settings only to its build invocation; the generated Xcode project retains the
official defaults. About shows `Codeg-Fork · <short SHA>`. Commit changes before
building a review artifact so this marker identifies its source.

The product and Swift module remain `Codeg`, and the output is `Codeg.app`.
Versions remain defined in `project.yml`. The preserved `scripts/release.sh` is
the upstream release workflow; it performs commits, tags, pushes, and releases.
Use the fork build script for local fork builds.

## Setup and signing

Install Xcode 26 with an iOS 26 simulator runtime, XcodeGen, and Python 3. The
first build resolves SwiftTerm through Swift Package Manager and needs network
access. Simulator builds do not need an Apple Developer account.

For signed device builds, configure your Apple ID in Xcode, then create the local
override if it does not already exist:

```bash
cp Config/Signing.local.xcconfig.example Config/Signing.local.xcconfig
```

Edit that ignored file with your own values:

```xcconfig
CODEG_DEVELOPMENT_TEAM = YOUR_TEAM_ID
CODEG_BUNDLE_ID_SUFFIX = .yourname
```

The dot-prefixed suffix is optional and affects only fork builds. Without it, the
bundle ID is `app.codeg.ios.fork`; the example produces
`app.codeg.ios.fork.yourname`. Keep local signing files, certificates, provisioning
profiles, tokens, and generated test fixtures out of version control.

## Build, run, and test

Choose an exact available simulator name from `xcrun simctl list devices available`.
The default is `iPhone 17`:

```bash
scripts/build-fork.sh --help
scripts/build-fork.sh sim --name "iPhone 17"
scripts/build-fork.sh test --name "iPhone 17"
scripts/build-fork.sh generic-device
scripts/build-fork.sh device --device "<device-name>"
```

| Command | Behavior |
| --- | --- |
| `sim` | Build, boot the selected simulator, install, and launch the fork. |
| `test` | Run `CodegiOSTests` on that simulator without parallel simulator clones. |
| `generic-device` | Build and sign for generic iOS, then verify the signature; no installation. |
| `device --device ...` | Build, install, and launch on the specified physical device; name or identifier required. |

Every command regenerates the project with XcodeGen and passes
`-skipMacroValidation`. Simulator commands disable signing; device commands use
automatic provisioning and the Xcode account session. Build output prints the
actual bundle ID and app path:

- Simulator/tests: `build/fork/simulator/Build/Products/Debug-iphonesimulator/Codeg.app`
- Device: `build/fork/device/Build/Products/Debug-iphoneos/Codeg.app`

Use separate checkout/build directories and simulator names for concurrent runs.
Shut down your selected simulator when finished:

```bash
xcrun simctl shutdown "iPhone 17"
```

The normal unit suite uses local fixtures. Optional TLS integration cases skip
unless a generated fixture is present. Run `scripts/test-pinning.sh --name "iPhone 17"` to generate
an ephemeral certificate and exercise HTTPS/WSS pinning, headers, redirects, and
endpoint switching against a loopback fixture. It uses `127.0.0.1:18455` by
default (`FORK_TLS_TEST_PORT` overrides the port) and cleans up its recorded
server process and temporary credentials on exit.
`scripts/test-pairing-paste.sh --name "iPhone 17"` runs the unit suite, including
pairing tests, with compact output.

### Optional UI automation and server harness

The generated `E1bUI` scheme contains the `CodegiOSUITests` target. Its driver
skips unless the ignored `CodegiOSUITests/E1bController.json` is present. That
file supplies a loopback controller `url` and an optional `bundleID`; the default
is `app.codeg.ios.fork`. Set the actual fork bundle ID when using a signing suffix.

`scripts/f3-e2e.py` is an optional simulator adapter. It needs a separate codeg
server checkout containing an `e2e/` harness; this repository does not ship that
harness, and a stock server checkout may not contain it. The required modules are:

- `harness.py`: `api`, `load_state(name)`, and `state_path(name)`.
- `ui_bridge.py`: a controller `Handler` and replaceable `load_state`.
- `ui_command.py`: `ui(command, name)` with `CONFIG` and `EVIDENCE` paths.
- `e1b_lifecycle.py`: `stop_server(state)` and `start_server(state, port)`.

Prepare a disposable environment with that harness first. Its state must provide
`server_port`, `relay_url`, `token`, and `fingerprint`; `seed` also needs the
matching `.session.json` with `connectionId`, `folderId`, and `conversationId`.
The adapter clears inherited `CODEG_*` environment variables and selects the
environment explicitly:

```bash
python3 scripts/f3-e2e.py --help
python3 scripts/f3-e2e.py bridge \
  --server-checkout /path/to/codeg-server \
  --state-name demo \
  --evidence-dir .codex/e2e
```

Build the fork simulator app before starting the bridge; `--app-path` can select
another build. The bridge writes the ignored controller configuration. Keep it
running while executing the UI scheme with the same fork flavor settings and
simulator, and use `ui '<JSON command>'` with the same required options to send
commands. `proxy` additionally requires `--proxy-url <status-url>`.

`move-home` and `restore-home` stop/restart the selected harness server to exercise
failover, and `seed` submits a synthetic prompt to its session. Use only disposable
environments for these actions. Stop the bridge, remove its controller JSON, and
shut down the test simulator after use. Evidence can contain transcript content;
keep it in the ignored `.codex/` directory.

## Connect and pair

For a LAN connection, add a server URL and token, select **Test Connection**, then
**Save**. For relay access, scan the server's pairing QR code or expand **Paste
pairing code** on the welcome screen or in Add/Edit Server. You can paste with the
system button or type a code and select **Import pairing code**. Review the
imported fields and save; cancelling discards the draft.

The importer accepts version 1 pairing JSON (`v`, `mode`, `url`, `token`, optional
`fp` and `name`), legacy URL JSON, plain URLs, and URLs with a `token` query
parameter. A fingerprint is the SHA-256 of the leaf certificate DER, not its
public key. Pins require HTTPS. Invalid pins reject the import without partially
changing the editor.

For a self-signed endpoint, **Test Connection** displays its fingerprint. Check
it against a trusted source before choosing **Trust this certificate**. This
stages the pin; **Save** persists it. A changed certificate is rejected even if
system-trusted. **Replace pin** requires a separate confirmation. Unpinned
connections use system trust.

When importing a relay code into an existing LAN profile, choose to keep LAN and
add/replace the secondary relay, replace the primary, or cancel. Both endpoints
must represent the same server and share its token and custom headers. Each
endpoint keeps its own certificate pin.

## Headers and connection recovery

Add custom name/value headers in the server editor. Values are stored with the
token in Keychain and apply to HTTP and WebSocket requests. Reserved transport
and authorization headers, duplicate names, and invalid characters are rejected.
Authenticated redirects stay on the same scheme, host, and port.

The client probes both endpoints on startup, meaningful network changes, and
transport failures. LAN probes have a 1.5-second budget; relay probes have a
5-second budget. Healthy LAN is preferred on Wi-Fi, while a failure can select a
healthy alternative immediately. The server row and session header show the
active LAN/Relay endpoint. Authentication, validation, and certificate errors do
not silently trigger a trust change or repeated failover.

Large streaming snapshots count received-byte progress as liveness. Heartbeats
and `NWPathMonitor` detect lost connections or network changes. Active turns keep
reconnecting with capped backoff and sequence cursors. When a reply completes
during a gap, the client reconciles persisted transcript data while protecting
nonempty streamed content. Recovery still depends on the server's available
history and live-session state. Requests that may already have sent a mutation
are reconciled instead of blindly replayed. Terminal sessions reconnect to their
PTY, but terminal output produced during disconnection is not replayed.

## Transcripts, agents, and folderless chat

Sessions initially request a 60-turn tail window. **Load earlier messages** uses
the server's offsets and prefix hashes, preserving a stable visible-row anchor
after prepending older content. A history mismatch refreshes the tail. Older
servers without window metadata continue to return complete history.

Custom and unknown agent types retain their full server identifiers. Catalog
names are used when available; unavailable metadata falls back to derived names
and generic icons instead of changing the agent's identity.

Choose **Chat (no folder)** in New Task or **Start chat (no folder)** in the empty
state. Chat sessions appear in the **Chat** group, with pinned chats in **Pinned**.
They support normal transcript loading, rename, pin, and delete actions, and hide
repository branch controls. A failed first send keeps the created chat available
for retry; an unused empty chat can be deleted through the session menu.

## Troubleshooting and removal

- **Simulator not found or ambiguous:** select one exact available name with
  `--name`, or rename duplicate simulators in Xcode.
- **Signing/provisioning failure:** check your Xcode account, team ID, unique
  bundle suffix, and local signing override; retry `generic-device` to verify.
- **TLS mismatch:** compare the displayed fingerprint with the server's current
  certificate before explicitly replacing a saved pin.
- **Relay offline or unauthorized:** check the server's relay client, token, and
  required proxy headers. LAN support alone does not imply relay pairing support.
- **Network/attachment error:** follow the localized timeout, offline, rate-limit,
  or size guidance. Rate limits show the server's retry delay when available;
  cancellation does not surface as an error.
- **Chat unavailable:** confirm the server supports `create_chat_dir` and
  `create_chat_conversation`; a 404/501 disables entry for that transport lifetime.

Fork OS links use `codegfork://`, for example `codegfork://tab/settings`.
In-app `codeg://` content links retain their meaning. To uninstall, use the exact
fork bundle ID printed by the build script and the intended simulator:

```bash
xcrun simctl uninstall "iPhone 17" app.codeg.ios.fork.yourname
```

Deleting the app removes its container, but iOS may retain Keychain items. Delete
server profiles in the app first if their saved credentials should be removed.
Local build artifacts are under this checkout's `build/fork` directory.
